# Diagnóstico de bugs web

Pide un diagnóstico que termine en una causa respaldada por evidencia, una corrección acotada y una comprobación que pueda detectar la regresión. Aplica las comprobaciones de reproducción a fallos funcionales y de rendimiento. Para riesgos de acceso indebido, exposición de datos u otra debilidad de seguridad, usa la [revisión defensiva](seguridad-web.md) para analizar y validar el control.

1. **Delimita el síntoma**. Indica el comportamiento esperado y el observado, la ruta o acción que falla, el entorno y los datos de prueba necesarios. Para un bug funcional, pide el caso mínimo reproducible en un entorno local o de pruebas. Si solo hay un reporte, identifica la traza, el archivo o la condición que falta comprobar.
2. **Sigue el flujo real**. Empieza por el punto de entrada y localiza la primera discrepancia. En el navegador, revisa estado, renderizado, consola y red según el síntoma. En el servidor, sigue la ruta, el middleware, el servicio y las transiciones de datos que participan. Relaciona errores de navegador y servidor mediante la petición o un identificador de registro cuando exista.
3. **Contrasta las hipótesis**. Prioriza las explicaciones que encajen con lo observado. Indica qué comprobación permitiría descartar o confirmar cada candidata relevante. Vincula la causa confirmada a una ruta, función, registro o prueba. En rendimiento, mide con las mismas condiciones antes y después, y elige una métrica relacionada con la demora que percibe el usuario.
4. **Corrige la causa y verifica**. Si el encargo incluye editar, aplica el cambio en el punto donde se origina el fallo y conserva los contratos de los demás flujos. Reutiliza las pruebas o los scripts del repositorio. Comprueba el camino normal, la condición que provocó el fallo y los casos límite afectados. Registra qué se ejecutó, qué resultado dio y qué evidencia falta para cerrar el diagnóstico.
